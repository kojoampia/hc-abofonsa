## C1 — The seeded `user` / `user` account is live in production

**Severity: Critical · A07 Identification and Authentication Failures (with A01)**

`src/main/resources/config/liquibase/data/user.csv` seeds two accounts, not one:

```
1;admin;$2a$10$gSAhZrxMllrbgj/kkK9UceBPpChGWJA7SYIb1Mqo.n5aNLq1/oRrC;...;true;...
2;user;$2a$10$VEjxo0jq2YG9Rbk2HmX9S.k1uZBGYUHdUcid3g/vfiEl7lwWgOH/K;...;true;...
```

Both hashes were verified locally with bcrypt: row 1 is the password `admin`, row 2 is the password
`user`. Both rows are `activated=true`, and `user_authority.csv` grants account 2 `ROLE_USER`.

Three things combine:

1. The `loadData` changeset in `00000000000000_initial_schema.xml:57` carries **no `context`
   attribute**, so unlike the content seeds (`contextFilter="!test"`) it runs under every profile,
   including `prod`. No later changelog deletes or deactivates the row.
2. `AdminAccountInitializer` resets **only** the `admin` login
   (`AdminAccountInitializer.java:29`, `ADMIN_LOGIN = "admin"`). `ABOFONSA_ADMIN_PASSWORD` — which
   the deploy tooling correctly requires — never touches account 2.
3. `SecurityConfiguration.java:73` grants every authenticated principal the whole entity API:
   `.requestMatchers("/api/**").authenticated()`.

So anybody on the internet can `POST /api/authenticate` with `user` / `user`, receive a valid
24-hour JWT, and reach everything under `/api/**` that is not explicitly `/api/admin/**`:

- `GET /api/waitlist-signups` — **every captured email address**, plus `fullName`, `organisation`,
  `ipHash`, `userAgent` and `confirmationToken`, paginated and filterable.
- `PUT`/`DELETE /api/waitlist-signups/{id}` — alter or destroy the waitlist.
- `GET /api/capture-events`, `/api/metric-rollups`, `/api/data-export-logs` — the analytics log and
  the record of who exported what.
- `PUT /api/launch-settings/{id}`, `/api/pledge-tier-teasers/{id}`, `/api/social-links/{id}` — the
  content the public launch page renders. `launch.fundUrl` and `tier.handoffUrl` are rendered
  straight into the pledge call-to-action, so this is a route to pointing donors at an attacker's
  payment page.
- `POST /api/register` — `AccountResource.registerAccount` is under `/api/**`, so an authenticated
  principal can create further accounts.

The one thing it cannot reach is `/api/admin/**`, which means the CSV export and the metrics API are
safe. That is small comfort: `GET /api/waitlist-signups?size=2000` returns the same personal data the
export does, without an audit row in `data_export_log`.

The CLAUDE.md statement that "there is one privileged account, seeded by Liquibase" is accurate about
privilege and wrong about count — the second account is unprivileged relative to `admin` but not
relative to the data.

**Recommendation.** Order matters; do (1) on the server today.

1. **Immediate:** on webserver, deactivate the row —
   `docker exec abofonsa-preview-postgres psql -U abofonsaPreview -d abofonsaPreview -c "update jhi_user set activated = false, password_hash = '!' where login = 'user';"`
   Confirm before and after with a `POST /api/authenticate` for `user`/`user`: 200 before, 401 after.
2. **Permanent:** add a Liquibase changeset that deletes login `user` and its authority rows, so a
   fresh database never has it. Deleting the row from `user.csv` alone does nothing — the initial
   changeset is already applied and checksummed, so a new changeset is the only route.
3. **Defence in depth:** extend `AdminAccountInitializer` to fail startup (or deactivate) on any
   account whose password still matches a known generator default, rather than trusting the seed.
4. Fix H1 below, so that a stray account cannot reach the data even if one reappears.

## H1 — `/api/**` requires only authentication, never `ROLE_ADMIN`

**Severity: High · A01 Broken Access Control**

`SecurityConfiguration.java:72-73`:

```java
.requestMatchers("/api/admin/**").hasAuthority(AuthoritiesConstants.ADMIN)
.requestMatchers("/api/**").authenticated()
```

Only the two hand-written admin controllers live under `/api/admin/**`
(`AdminExportResource`, `AdminMetricsResource`, both additionally `@Secured(ADMIN)`). Every
JHipster-generated entity controller sits at the bare path — `/api/waitlist-signups`,
`/api/capture-events`, `/api/data-export-logs`, `/api/launch-settings`, `/api/social-links` and the
rest — and carries no method-level annotation. `AuthorityResource` and `UserResource` are the only
generated controllers with `@PreAuthorize`.

The application's own model is that there is exactly one human, an administrator. Authorisation
should say so. As written, "logged in at all" and "may read the whole waitlist" are the same
permission, which is what turns C1 from an embarrassment into a data breach.

**Recommendation.** Make `ROLE_ADMIN` the default for the authenticated surface:

```java
.requestMatchers("/api/public/**").permitAll()
.requestMatchers(HttpMethod.POST, "/api/authenticate").permitAll()
.requestMatchers("/api/account", "/api/account/change-password").authenticated()
.requestMatchers("/api/**").hasAuthority(AuthoritiesConstants.ADMIN)
```

Then add `@Secured(AuthoritiesConstants.ADMIN)` at the class level on each generated resource, so the
protection survives someone re-running the entity generator or editing the URL rules — the same
belt-and-braces the two admin controllers already have. Note the generated `*ResourceIT` tests
authenticate as `ROLE_USER` via `@WithMockUser`; they will need `authorities = "ROLE_ADMIN"`.

## H2 — No security headers on any HTML response

**Severity: High · A05 Security Misconfiguration**

Verified live. The API sends the full header set:

```
$ curl -sSI https://abofonsa.com/api/public/content
x-content-type-options: nosniff
x-frame-options: SAMEORIGIN
content-security-policy: default-src 'self'; frame-src 'self' data:; script-src 'self' ...
referrer-policy: strict-origin-when-cross-origin
permissions-policy: camera=(), fullscreen=(self), ...
```

Every HTML document sends none of them:

```
$ curl -sSI https://abofonsa.com/          # and /login, and every SPA route
HTTP/2 200
server: nginx
content-type: text/html
last-modified: Thu, 01 Jan 1970 00:00:01 GMT
(no CSP, no X-Frame-Options, no Referrer-Policy, no X-Content-Type-Options)
```

A Content-Security-Policy on a JSON response protects nothing — CSP governs the document that loads
the scripts, and that document is the one being served bare. The same is true of `X-Frame-Options`
and `Referrer-Policy`. In effect the application currently has **no CSP and no clickjacking
protection in the browser at all**, despite both being configured.

The cause is `SpaWebFilter` (`web/filter/SpaWebFilter.java:27`): it answers unmapped paths with
`request.getRequestDispatcher("/index.html").forward(request, response)`. The forward dispatch does
not re-enter the security filter chain, and the response is committed by the target servlet without
the header writers having run.

This matters more here than it usually would, because `state-storage.service.ts:28` keeps the JWT in
`localStorage` — a script-readable location. With no CSP, any injected script exfiltrates an admin
session; and `/login` being framable is a straightforward clickjacking target.

**Recommendation.** Two independent fixes; do both.

1. Add the headers at the edge, in `deploy/prod-server/abofonsa-preview.conf`, with `add_header ...
   always` so they attach regardless of status code. This covers static and forwarded responses
   alike and is one file to review. Note that certbot rewrites this file, so re-check after renewal
   changes.
2. Register the security filter chain for `FORWARD` as well as `REQUEST` dispatch, or have
   `SpaWebFilter` serve `index.html` directly instead of forwarding, so Spring Security's configured
   headers apply to the document. Assert it in `SpaWebFilterIT` — a header regression is invisible
   without a test.

## H3 — No HSTS, and the application never learns the request was HTTPS

**Severity: High · A02 Cryptographic Failures (with A05)**

`http://abofonsa.com` correctly 301s to HTTPS, but no response on either scheme carries
`Strict-Transport-Security`. Certbot's nginx rewrite does not add it, and the nginx config does not
either. Without HSTS, the very first request of every visit — the one the redirect answers — is
plaintext and strippable.

Spring Security would normally supply the header itself, but cannot here: it only emits HSTS for
requests it believes are secure, and `application-prod.yml` does not set
`server.forward-headers-strategy`. Only `application-dev.yml` sets it (`native`, line 52). In
production the app is behind nginx over plain HTTP on loopback, so `request.isSecure()` is false, and
the header is suppressed. The same gap means `ServletUriComponentsBuilder` — used to build the
pagination `Link` headers in `PublicUserResource` and every generated resource — will produce
`http://` URLs.

**Recommendation.**

- Add `Strict-Transport-Security: max-age=31536000; includeSubDomains` in the nginx TLS server block
  (`always`). Consider `preload` only once you are confident about every subdomain of
  `abofonsa.com`, since `web.` and `fund.` are siblings on the same apex.
- Set `server.forward-headers-strategy: framework` in `application-prod.yml` so the app honours
  `X-Forwarded-Proto` — nginx already sends it. This also makes any Spring-side HSTS and secure-cookie
  logic behave.

## H4 — Eight high-severity Angular advisories in the shipped bundle

**Severity: High · A06 Vulnerable and Outdated Components**

`npm audit --omit=dev` at this commit:

```
9 vulnerabilities (1 low, 8 high)
```

`package.json` pins `@angular/*` at exactly `21.2.14`; the advisories are fixed in **21.2.19**, a
patch release inside the same minor. (`npm audit fix --force`'s warning about "outside the stated
dependency range" is an artefact of the exact pin, not a major-version jump.)

The relevant ones for this app, since it renders administrator-supplied content into a page that
holds an admin JWT in `localStorage`:

- `@angular/compiler` — Two-Way Property Binding Sanitization Bypass (XSS) — GHSA-58w9-8g37-x9v5
- `@angular/core` / Angular — Template and Attribute Namespace Sanitization Bypass (XSS) —
  GHSA-f3m7-gqxr-g87x
- `@angular/localize` — XSS via event-handler attributes in i18n — GHSA-jj27-h5hq-8x99
- `@angular/common` — DoS via OOM in `formatDate`; weak 32-bit cache-key hashing
- `@babel/core` ≤ 7.29.0 — arbitrary file read via `sourceMappingURL` (build-time only, low)

These are sanitiser bypasses, and this codebase leans on the sanitiser: `alert.service.ts:66`
sanitises alert text before it is bound through `[innerHTML]` in `alert.html` and
`alert-error.html`, and `translate.directive.ts:47` assigns to `innerHTML` directly. With H2
unresolved there is no CSP to act as a second layer.

**Recommendation.** Bump every `@angular/*` pin to `21.2.19`, re-run `npm test`,
`npm run webapp:build:prod` and the Cypress suite, and rebuild the image. Then add
`npm audit --omit=dev --audit-level=high` to `.github/workflows/publish.yml` so the next one is
caught by CI rather than by an audit (see L4).

## M1 — The waitlist rate limit is bypassable by spoofing `X-Forwarded-For`

**Severity: Medium · A04 Insecure Design**

`VisitorContextService.clientIp` (line 100) takes the **first** comma-separated entry of
`X-Forwarded-For`, falling back to the socket address. nginx sets that header with
`$proxy_add_x_forwarded_for` (`abofonsa-preview.conf:69`), which **appends** the real peer to
whatever the client sent. A request carrying `X-Forwarded-For: 203.0.113.9` arrives at the app as
`203.0.113.9, <real ip>` — and the first entry, the attacker's invention, is what gets hashed.

Consequences:

- **Rate limit defeated.** `WaitlistCaptureService.submit` counts prior signups by `ipHash`
  (line 74). A new spoofed value per request means the counter is always 0 and
  `ABOFONSA_WAITLIST_MAX_PER_HOUR` never bites. Combined with M4, the waitlist and `capture_event`
  can be flooded at will.
- **Metrics poisoned.** `sessionHash` mixes the same value, so `UNIQUE_VISITORS` — a headline tile on
  the dashboard — can be inflated arbitrarily by one client.
- **Attribution corrupted.** An attacker can make abusive signups hash to the same bucket as a chosen
  third party's address.

The salting is done properly, and it is the salting that makes this worth fixing rather than
shrugging at: the hashes are otherwise trustworthy, so they read as evidence.

**Recommendation.** Trust only what the proxy asserts. Simplest and most robust here: read
`X-Real-IP`, which `abofonsa-preview.conf:66` sets unconditionally from `$remote_addr` and which a
client therefore cannot influence. Alternatively, take the **last** `X-Forwarded-For` entry, or
configure a trusted-proxy count and index from the right. Keep the socket-address fallback for
direct/dev access. `VisitorContextService` is unit-testable without a container, so this deserves a
test asserting that a forged header does not change the hash.

## M2 — No brute-force protection on `POST /api/authenticate`

**Severity: Medium · A07 Identification and Authentication Failures**

`AuthenticateController.authorize` performs an unlimited number of password attempts. There is no
lockout, no delay, no per-IP throttle and no CAPTCHA; nothing in `pom.xml` provides rate limiting.
`LoginVM` allows a 4-character password (`@Size(min = 4)`), and `AccountResource`'s length check
is not on this path at all.

There is also no record of the attempt. `SecurityMetersService` counts *token* problems — invalid
signature, expired, malformed — but a failed username/password login produces no metric and no log
line, so a sustained guessing campaign against the single administrator account is invisible in both
the logs and Prometheus. That is the A09 (Logging and Monitoring) half of the same gap.

The waitlist endpoint, by contrast, is rate limited. The asymmetry is the wrong way round: the
endpoint that guards the admin session is the unprotected one.

**Recommendation.**

- Throttle by client identity — the same corrected client-IP derivation as M1 — with an escalating
  delay or a short lockout after ~10 failures. Bucket4j is the usual JHipster choice; an in-memory
  Caffeine counter is enough for a single-instance deployment.
- Log failures at WARN with the login attempted and the derived client hash, and add a
  `security.authentication.failure` counter to `SecurityMetersService` so the existing Prometheus
  scrape can alert on it.
- Raise `LoginVM`'s minimum to match `ManagedUserVM.PASSWORD_MIN_LENGTH`.

## M3 — `confirmationToken` is readable and filterable over the entity API

**Severity: Medium · A01 Broken Access Control (with A02)**

`WaitlistSignupDTO` carries `confirmationToken` (line 70) alongside `ipHash` and `userAgent`, and
`GET /api/waitlist-signups` returns it in every row. `WaitlistSignupCriteria` also exposes it as a
`StringFilter` (line 131), so it can be queried with `contains` / `startsWith` — a character-by-character
oracle, no full-table read required.

That token is the credential for `GET /api/public/waitlist/confirm` and `/unsubscribe`, both
anonymous. Anyone who can read it can confirm a signup on someone else's behalf — defeating double
opt-in, which is the consent record — or unsubscribe them.

The project's own convention says this should not happen: "Public payload DTOs are hand-written
records, not the generated entity DTOs — so adding an internal field to an entity cannot silently
publish it." The convention holds for `/api/public/**`; the generated admin CRUD DTO is where it
leaks. `PublicWaitlistResource.submit` is careful to strip the token from its own response
(line 49), which shows the intent clearly.

A secondary issue on the same object: `WaitlistSignupResource` logs the whole DTO
(`LOG.debug("REST request to save WaitlistSignup : {}", waitlistSignupDTO)`), and
`WaitlistSignupDTO.toString()` includes the email, the token and the IP hash. Production runs at
INFO so this does not fire there, but the dev profile logs the application package at DEBUG.

**Recommendation.** Drop `confirmationToken`, `ipHash` and `userAgent` from `WaitlistSignupDTO` and
from `WaitlistSignupCriteria` — the dashboard does not render any of them — or annotate them
`@JsonProperty(access = WRITE_ONLY)` at minimum. Redact them from `toString()` too. Since
re-running the entity generator restores all of this, it belongs in the CLAUDE.md
"re-generating will reintroduce this" list beside the `@JdbcTypeCode` note.

## M4 — The analytics beacon is anonymous and unthrottled

**Severity: Medium · A04 Insecure Design**

`POST /api/public/events` is `permitAll` and performs an unbounded insert into `capture_event` per
request (`CaptureEventRecorder.record`). The event-type allow-list is well judged — the
server-attested types cannot be forged, which protects the signup count — but nothing limits volume.
An unauthenticated client can grow the table without bound, which is both a cheap denial of service
against a single small Postgres instance and a way to swamp `PAGE_VIEWS` and the campaign-source
split with fabricated data. With M1 unfixed, per-client throttling would not stop it anyway.

**Recommendation.** Apply a per-client cap (a Caffeine counter keyed on the corrected client hash is
enough — the beacon fires a handful of times per visit, so a limit in the low hundreds per hour is
generous), and consider a nginx `limit_req` zone on `/api/public/` as a second, independent layer.
Add a size cap on the JSON body while you are there; the fields are `@Size`-bounded but the request
is not.

## M5 — The CSP permits `unsafe-inline`, `unsafe-eval` and an external script origin

**Severity: Medium · A05 Security Misconfiguration**

`application.yml`, `jhipster.security.content-security-policy`:

```
script-src 'self' 'unsafe-inline' 'unsafe-eval' https://storage.googleapis.com
```

This is JHipster's stock value, carried over unchanged. `unsafe-inline` and `unsafe-eval` remove most
of what a script-src is for, and `https://storage.googleapis.com` is a shared bucket host that this
application does not use — a legacy of the generator's Swagger UI defaults. `frame-src 'self' data:`
is likewise broader than anything the launch page needs.

This is listed below H2 because today the policy is not delivered to the browser at all; once H2 is
fixed, this becomes the policy that is actually in force, so the two should be fixed together.

**Recommendation.** Tighten to what the app needs and verify against the built bundle:

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' data:; font-src 'self' data:; frame-ancestors 'none';
base-uri 'self'; form-action 'self'; object-src 'none'
```

Angular's production build needs neither `unsafe-inline` nor `unsafe-eval` for scripts;
`style-src 'unsafe-inline'` is still required for Angular's runtime style injection.
`frame-ancestors 'none'` supersedes `X-Frame-Options` in modern browsers. Test the admin dashboard's
charts explicitly — chart libraries are the usual thing that trips over a strict `script-src`.

## L1 — Side-effecting GETs on a token that never expires

**Severity: Low · A04 Insecure Design**

`GET /api/public/waitlist/confirm?token=…` and `…/unsubscribe?token=…` both mutate state on a GET.
Email clients and security gateways routinely prefetch links, so a scanner can confirm a signup that
the human never clicked — quietly weakening double opt-in as a consent record — or unsubscribe them.

Compounding it: `confirmationToken` has no expiry (`WaitlistCaptureService.newToken`, and nothing
clears it after use), and the *same* token serves both confirm and unsubscribe. A link forwarded or
sitting in an old mailbox stays valid forever and does both jobs.

**Recommendation.** Land on an HTML confirmation page and complete the action with a `POST` from
there; or, if that is too heavy for a preview site, accept the GET but give the token an expiry
(72 hours is conventional) and issue a **separate**, longer-lived token for unsubscribe. Regardless
of the mechanism, per RFC 8058 an unsubscribe link should be one-click — the fix is separating the
two capabilities, not adding friction to opting out.

## L2 — Long-lived JWTs in `localStorage`, with no revocation

**Severity: Low · A02 Cryptographic Failures**

`state-storage.service.ts:28` stores the token in `localStorage` when "remember me" is ticked and
`sessionStorage` otherwise. Both are script-readable, so any XSS yields an admin session. Validity is
24 hours, or **30 days** with remember-me (`application-prod.yml`), and being stateless the tokens
cannot be revoked — rotating `JWT_BASE64_SECRET` is the only lever, and it signs everyone out.

`csrf.disable()` in `SecurityConfiguration.java:41` is correct *given* this design — a token in
`localStorage` is not sent ambiently, so there is no CSRF to defend. That coupling is worth stating
explicitly: it means switching to cookie-based auth later requires re-enabling CSRF in the same
change.

This is Low because the practical exposure is governed by H2 and H4 above, both of which are the
real fixes. If you later want to reduce it directly, the standard shape is a short-lived access
token in memory plus a refresh token in an `HttpOnly; Secure; SameSite=Strict` cookie — a meaningful
piece of work for a one-account preview site, so probably not now.

Reducing remember-me from 30 days to something like 7 costs nothing and is worth doing.

## L3 — `/management/**` is `permitAll` in the application

**Severity: Low · A05 Security Misconfiguration**

`SecurityConfiguration.java:75-78` permits `/management/health`, `/management/health/**`,
`/management/info` and `/management/prometheus` anonymously. `/management/prometheus` publishes the
full micrometer registry — endpoint URIs, request counts and latency percentiles across the whole
API, plus JVM internals.

In the current deployment this is not reachable: nginx returns 404 for `/management` (verified —
both `/management/health` and `/management/prometheus` answer 404 from outside), and the container
publishes only to loopback. So the exposure is confined to anything on the shared `monitoring`
Docker network, which is where Prometheus scrapes from and where it needs to be anonymous.

The comment in the nginx config frames this as two independent layers. Strictly, one layer is doing
the work; the application-side rule is `permitAll`. Worth recording so that a future change to the
nginx site — or a deployment without it — is understood to remove the only control.

**Recommendation.** Leave `/management/health` anonymous (the Docker healthcheck needs it; details
are already `when_authorized`). Restrict `/management/prometheus` to `ROLE_ADMIN` and give Prometheus
a bearer token, or bind the management endpoints to a separate port that is published only on the
monitoring network. Trim the exposure list in `application.yml` too — `env`, `configprops`,
`threaddump` and `logfile` are admin-gated but need not be exposed at all in production.

## L4 — CI actions pinned to mutable tags; no dependency scanning or SBOM

**Severity: Low · A08 Software and Data Integrity Failures**

`.github/workflows/publish.yml` is otherwise a careful piece of work — least-privilege
`permissions:`, no daemon build, credentials written to the config file rather than the command line
(with the `ps` reasoning noted in a comment), and a post-push verification step. Two gaps remain:

- Actions are pinned to mutable major tags (`actions/checkout@v4`, `actions/setup-java@v4`,
  `actions/cache@v4`, `docker/login-action@v3`). A compromised or retagged action runs with
  `packages: write` in a job that also holds the GHCR token.
- Nothing scans dependencies. H4's eight high-severity advisories would have been caught by the
  build that produced the currently deployed image.
- No SBOM or image signature, so "what is in the running image" cannot be answered after the fact —
  which is the question an advisory forces on you.

**Recommendation.** Pin actions to full commit SHAs with the version in a trailing comment, and let
Dependabot bump them. Add `npm audit --omit=dev --audit-level=high` and an OWASP Dependency-Check
(or Trivy) pass on the built image, failing the build on high. If it fits, generate an SBOM with the
jib plugin and attach it to the package.

## L5 — Disabled account-management endpoints and UI are still shipped

**Severity: Low · A01 Broken Access Control**

`AccountResource` still maps `/api/register`, `/api/activate`,
`/api/account/reset-password/init` and `/api/account/reset-password/finish`. They are unreachable
anonymously — `SecurityConfiguration` deliberately does not permit them, and the comment at line 68
explains why — but they are *not* unreachable: they fall under `.requestMatchers("/api/**")
.authenticated()`, so any authenticated principal can call them. Under C1 today, that means
`user`/`user` can register accounts and trigger password-reset emails.

The Angular side still ships the pages: `account.route.ts` registers `registerRoute`,
`passwordResetInitRoute`, `passwordResetFinishRoute` and `activateRoute`, and
`navbar.html:373` still links to `/account/register`. The login page's links were removed and there
is a comment explaining it (`login.html:55`), so this looks like the navbar was simply missed.

The whole arrangement rests on one URL-matcher line. That is a thin margin for endpoints that create
accounts and reset passwords.

**Recommendation.** Delete the four handler methods from `AccountResource` and the corresponding
Angular routes and components, keeping `/api/account` and `/api/account/change-password`. Remove the
navbar entry. The `@Disabled` tests should follow the code out rather than be left asserting
behaviour that no longer exists. If you would rather keep the code, add
`.requestMatchers("/api/register", "/api/activate", "/api/account/reset-password/**").denyAll()`
above the `/api/**` rule, so the intent is stated positively rather than by omission.

## Categories with no findings

**A03 Injection.** Clean, and deliberately so. All four native queries
(`CaptureEventRepository`, `WaitlistSignupRepository`) bind every value, including the `date_trunc`
unit, via `cast(:unit as text)` — the one place a string could plausibly have been concatenated. JPQL
elsewhere is parameterised, and Specification-based criteria queries are built through the JPA
Criteria API. `DataExportService.csvCell` neutralises spreadsheet formula injection on `= + - @` and
tab/CR, which is the injection vector this app actually has, and the reasoning is in a comment.
Angular's default interpolation escapes output; the two `[innerHTML]` bindings are fed from
`AlertService`, which sanitises through `DomSanitizer` first. No `bypassSecurityTrust*` calls exist
anywhere in the codebase.

**A10 Server-Side Request Forgery.** No user-controlled outbound requests. `MailService` talks only
to the configured SMTP host. `VisitorContextService.referrerHost` parses the `Referer` header but
only to extract and store a hostname — it never dereferences it, and it deliberately discards the
path so that a referrer's query string or document title is never stored.

## Controls that are already right

Worth recording, both because they narrow the blast radius of the findings above and because they
should not be lost in a later refactor:

- **Secrets are required, not defaulted, in production.** `compose.yml` uses `${VAR:?message}` for
  `POSTGRES_PASSWORD`, `JWT_BASE64_SECRET`, `ABOFONSA_ADMIN_PASSWORD` and `ABOFONSA_HASH_SALT`, so
  the stack refuses to start rather than booting on a committed sample. `deploy.sh --bootstrap`
  generates them with `openssl rand` on the server, so they never touch the deploying machine.
- **The committed JWT sample key is confined to the `dev` profile group**, and `compose.yml` sets
  `SPRING_PROFILES_ACTIVE: prod` with a comment explaining exactly why `secret-samples` must not be
  added. That reasoning is correct and load-bearing.
- **Container hardening**: non-root (`<user>1000</user>` in the jib config), `read_only: true` with
  an explicit `/tmp` tmpfs, `cap_drop: ALL`, `no-new-privileges:true`, Postgres publishing no port,
  and the app published only on loopback.
- **Privacy engineering in `VisitorContextService`**: salted SHA-256 for both hashes, the session
  hash rotating at UTC midnight so it cannot be joined across days, referrer reduced to a host, and
  the user agent truncated. The stated threat model — that unsalted IP hashes are reversible in
  minutes — is right, and the salt is correctly treated as a required secret.
- **Anti-abuse on the capture path**: honeypot field, dwell-time check, per-client hourly cap, and a
  rejection message that does not tell a bot which check it failed.
- **Server-attested event types cannot be forged** — `PublicEventResource.BROWSER_REPORTABLE` is an
  allow-list, and the signup-count metrics are written only by the server when the thing happens.
- **Exports are audited.** Every CSV download writes a `data_export_log` row with who, when, range
  and row count. (Note that H1 provides a route to the same data *without* that row — another reason
  to fix it.)
- **Double opt-in tokens are not echoed** in the public submit response, with the reasoning in a
  comment at `PublicWaitlistResource.java:48`.
- **`ExceptionTranslator` suppresses internal detail**, replacing any message containing a package
  name with "Unexpected runtime exception".
- **`CriteriaBinderAdvice`** disables header binding into model attributes globally — a correctness
  fix, but also one that closes a class of parameter-injection surprises.

## A bug found while fixing L1

The emailed confirmation link has always pointed at `/confirm`, and the Angular router had
`/confirmed` and `/unsubscribed` but no `/confirm` — so **every confirmation link ever sent landed on
the 404 page** and double opt-in could not be completed by anyone. It went unnoticed because no SMTP
server is configured, so the links have only ever been written to the log. The new `/confirm` and
`/unsubscribe` routes fix it.

## Note on H2 — resolved at the edge, and the Spring cause is still unknown

The Spring-side change did **not** fix it. After deploying, `GET /` still returned no headers, so
the headers are now asserted by nginx instead — `deploy/prod-server/abofonsa-security-headers.conf`,
included from both proxying locations, with `proxy_hide_header` before each `add_header` so that
`/api/**`, which does emit them from Spring, ends up with exactly one of each. Two
`X-Frame-Options` headers are worse than one: some browsers discard a duplicated one outright.

Verified live: `/` and `/login` now carry CSP, `X-Frame-Options`, `X-Content-Type-Options`,
`Referrer-Policy`, `Permissions-Policy` and HSTS, and `/api/public/content` carries exactly one of
each.

The underlying Spring behaviour remains unexplained, and is worth an issue rather than a guess.
`SecurityHeadersIT` boots a real container and the headers are present there, so it does not
reproduce outside the `prod` profile; and it is not nginx, since `curl http://127.0.0.1:8084/` on
the host was equally bare. The `dispatcher-types` setting stays because it states the requirement
explicitly, but it should be understood as documentation, not as the fix.

## Incident: the strict CSP took the launch page down to unstyled text

Worth recording, because the failure mode is invisible to every check in this document.

Tightening `script-src` to `'self'` broke the site the moment nginx started sending it. Angular's
`inlineCritical` optimization emits

```html
<link rel="stylesheet" href="styles-*.css" media="print" onload="this.media='all'">
```

and that `onload` is an inline event handler. The CSP refused it, so the stylesheet stayed
`media="print"`, so 243 kB of styles never applied. The page still returned 200 with correct
headers and correct JSON — every `curl` check passed. It was only visible in a browser.

Restored within minutes by allowing `'unsafe-inline'` in `script-src` as a stopgap, then fixed
properly: `optimization.styles.inlineCritical: false`, generator-jhipster's inline slow-loading
notice moved to `src/main/webapp/slow-load-notice.js`, and `build-plugins/check-index-csp.mjs`
chained onto `webapp:build:prod` to fail the build if an inline script or handler reappears. The
guard was tested against a deliberately broken `index.html`, not only a good one. The stopgap was
then removed and the strict policy re-verified in a browser on both `/` and `/login`.

Two lessons, both cheap to state and expensive to learn: a CSP change is a front-end change and
needs a browser to verify, and `curl` confirming a header is present says nothing about whether the
page still works.

## Deliberately not done

- **L2, the refresh-token rework.** Reducing remember-me to 7 days is in. Moving the access token
  out of `localStorage` into memory with an `HttpOnly` refresh cookie is a genuine piece of work for
  a one-account preview site, and the audit recommended against it now. It stays open, and its real
  mitigations — a strict CSP and a patched Angular — are both delivered.
- **L3, locking `/management/prometheus`.** Restricting it needs a matching credential in the
  monitoring stack at `~/webroot/00-admin/monitoring`, a different repository. Changing one side
  alone silently breaks the scrape. The exposure list is trimmed and nginx still 404s `/management`;
  the endpoint itself remains anonymous on the internal monitoring network.
- **The dev-dependency advisories.** `npm audit` without `--omit=dev` still reports 13, in
  `browser-sync`, `concurrently`, `generator-jhipster` and the Angular CLI's own dependencies. None
  reach a browser or the running application. Clearing them means bumping `generator-jhipster`
  itself, which is a separate change with its own regeneration risk.
